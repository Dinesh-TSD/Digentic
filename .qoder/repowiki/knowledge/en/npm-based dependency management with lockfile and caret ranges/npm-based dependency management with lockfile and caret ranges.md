## System / Approach

The project uses **npm** as its package manager for a single Next.js application. Dependencies are declared in `package.json` under `dependencies` and `devDependencies`, and the resolved tree is pinned by a committed `package-lock.json` (lockfileVersion 3). There is no monorepo workspace configuration, no vendoring of JS packages, and no private npm registry configured — all packages resolve from the public `https://registry.npmjs.org/`.

## Key files

- `package.json` — declares the project name (`nextjs`), version (`0.1.0`), scripts (`dev`, `build`, `start`, `lint`, `typecheck`), runtime dependencies, and dev dependencies.
- `package-lock.json` — full deterministic lockfile generated by npm; every transitive dependency has an explicit `resolved` URL pointing to `registry.npmjs.org` and a `sha512` integrity hash.
- `.gitignore` — excludes `node_modules/` so only manifests and the lockfile are tracked.

## Architecture and conventions

- **Single-package scope**: The repository contains one top-level `package.json`; there are no nested `package.json` files or workspaces, so dependency resolution is flat.
- **Version pinning style**: Runtime dependencies use **caret ranges** (`^`) to allow compatible minor/patch updates (e.g. `next: ^16.3.5`, `react: ^19.3.0`, `mongoose: ^9.10.0`). A few tooling/dev dependencies are pinned to exact versions (e.g. `@types/node: 20.6.2`, `postcss: 8.4.30`, `tailwindcss: 3.3.3`, `eslint: 8.49.0`, `typescript: 7.0.2`), likely to keep build toolchains stable.
- **Lockfile-driven installs**: Because `package-lock.json` is committed, `npm ci` will produce identical trees across environments; manual edits should go through `npm install` to regenerate the lockfile rather than editing it by hand.
- **No overrides/resolutions**: There is no `overrides` or `resolutions` field in `package.json`, nor any `.npmrc` file, so dependency hoisting and version deduplication follow npm's default behavior.
- **Peer dependencies**: Some packages declare peer deps (e.g. `@auth/mongodb-adapter` expects `mongodb: ^6`), but the project satisfies them via its own `mongodb: ^7.6.0` declaration — this is tolerated by npm without failing installs.
- **Dev-only toolchain**: TypeScript (`typescript: 7.0.2`) lives in `devDependencies`; it is used only for type checking via the `typecheck` script (`tsc --noEmit`) and is not shipped to production.

## Conventions and constraints

- All third-party code comes from the public npm registry; no private registries, scoped packages beyond the standard `@auth/*`, `@hookform/*`, `@types/*`, etc., are used.
- Lockfile is kept in sync with `package.json` — changes to dependencies must be applied through `npm install` so that `package-lock.json` stays authoritative.
- No vendored `node_modules` or bundled third-party JS assets exist outside of the lockfile-managed tree.
- Scripts centralize dependency usage: `dev`, `build`, `start`, `lint`, and `typecheck` are the only entry points, keeping tooling consumption uniform.
